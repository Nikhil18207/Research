## Abstract

Multi-tenant LLM platforms serve many customers off a single shared base model by hot-swapping lightweight LoRA adapters, keeping only a small working set resident in GPU memory and evicting the rest under an LRU policy. We show that adapter residency is externally observable through request timing alone, by any unprivileged co-tenant, without access to victim prompts, outputs, or shared cache keys. The measurement technique (prime-and-probe cache timing) is classical; the target is new — prior LLM-serving side channels leak prompt content via KV/prefix-cache overlap, while this channel operates at the adapter-management layer over an ordinary API.

We validate this on vLLM, on real hardware with real trained adapters, across three base models. Residency states separate from latency alone (AUC=1.00 hot-vs-disk-evicted, AUC=0.92 RAM-eviction — a filesystem-bridge confound partly inflates the former, §3.7), and an attacker can actively evict a target adapter and detect subsequent activity via prime-and-probe (AUC=1.00). This foundational signal survives the first objection we expect: an attacker who never names the victim's adapter, only watches its own for unexpected eviction, still detects activity at AUC=0.79-0.99 on an idle GPU. It does not clearly survive the second: under realistic contention at production scale, single-probe detection collapses to chance (advantage 0.55, CI includes values below 0.5, n=200) and we do not have solid evidence that aggregation recovers it — a genuine open question we measured rather than assumed either way, after a first, smaller attempt wrongly suggested it did recover. At a production-scale cache configuration (vLLM's own `max_cpu_loras` default, 16x this paper's working configuration), existence remains near-perfectly separable and identification holds at 82.5% under an idle GPU (90.0% with a recalibrated, train-set-optimistic threshold). Both are measured directly, since these are the conditions we expect a competently configured, realistically-scaled platform to actually be in. Extending identification from two to eight independently-tracked adapters (a single-label 8-way task) held at 100% (n=80): probe cost scales linearly with tracked-set size, accuracy does not degrade. Detection frequency also tracks victim request rate (Spearman ρ=0.55, p=2.5×10⁻⁸ overall; a weaker but still significant ρ=0.25-0.43 gradient survives among nonzero rates alone, confound-checked via a canary block and a discarded blocked-order pilot), supporting this paper's motivating scenario with a measurement rather than an assumption.

If adapter identifiers are *additionally* addressable across tenants — a real, well-documented misconfiguration, not a subtle one — the channel escalates to naming *which* tenant was active (98.3-100% four-way accuracy, ~1.6 bits/s) and leaking adapter rank (0.14ms/rank-unit on native storage, R²=0.47 — the 9p-bridged 3.42ms/rank-unit, R²=0.967 we first measured turned out to be a ~25x filesystem-bridge inflation, §3.7); we report this as the channel's upper bound under that specific condition, not the central claim. Concurrent attacker traffic measurably perturbs victim outputs under default serving; batch-invariant kernels eliminate this entirely, confirming a pure timing leak. Evaluating constant-time padding at two margins (T_MAX=150ms and 300ms, n=200 each), we caught and corrected a real error in our own analysis; properly measured, padding closes the finer which-tier distinction to chance but leaves a real residual on the hot-vs-evicted distinction (advantage 0.56-0.63) that a larger margin reduces but does not eliminate.

## 1. Introduction

Serving large language models efficiently at scale increasingly means serving *many* customized models off *one* shared backbone. Low-Rank Adaptation (LoRA) has become the standard mechanism for this: instead of hosting a separate fine-tuned copy of a multi-billion-parameter model per customer, a provider hosts one base model and swaps in a small (megabytes, not gigabytes) adapter per request. Systems like S-LoRA, Punica, and LoRAX, and production serving engines such as vLLM, all exploit this to pack tens to hundreds of tenants' customizations onto a single GPU.

That efficiency has a cost, and the cost is structural, not incidental. A GPU cannot hold every registered adapter resident simultaneously — only a small working set fits in the fast tier of the serving engine's adapter cache, with the rest evicted (typically under an LRU policy) to CPU memory or disk, to be reloaded on demand. This is a deliberate architectural response to the scaling constraint: realistic multi-LoRA deployments cannot keep every tenant's adapter resident in GPU memory and therefore must manage a bounded fast tier backed by slower storage. (The specific GPU/CPU/disk LRU hierarchy we study is one implementation of this broader pattern, not the only one — §6.2 verifies this directly rather than assume it.) It is also, we show, an information channel: whether a specific tenant's adapter is currently resident is not a private implementation detail — it is directly observable, from outside the trust boundary, by timing an ordinary request.

This matters because *residency is not neutral information*. An adapter becomes resident when its owning tenant's requests are actively driving it back into the cache. An unprivileged co-tenant on the same server — someone who has purchased ordinary API access, nothing more — can therefore learn, purely from how long *their own* requests take, whether a specific other customer is currently active, and in our strongest result, *which* other customer, out of several, is active. No access to the victim's prompts, outputs, or any shared cache key is required; the entire signal is the timing of the attacker's own traffic.

**Why this is a different target, not a different technique.** The measurement pattern we use — evict a shared resource, wait, re-probe to detect whether it was refilled — is not novel as a *technique*. It is the standard structure of cache-based side channels going back over two decades of architectural security research (prime+probe and its relatives against CPU cache hierarchies, more recently extended to GPU-resident state). We do not claim to have invented this technique, and claiming otherwise would be an easy, avoidable overclaim. What is new is the *layer* we apply it to: a software-managed, tenant-aligned cache (the adapter-management layer of a multi-LoRA serving stack) rather than a hardware cache line, observed over an ordinary HTTP API by a client with no co-located process and no need to construct eviction sets from cache-line geometry — properties that make this channel *more* accessible than the classical hardware instantiations of the same technique, not a harder variant of them. Within LLM serving specifically, the closest prior work — PromptPeek, EarlyBird, InputSnatch, and the broader line of KV-cache and prefix-cache timing attacks — targets a *different* layer (token-sequence cache keys) to leak a *different* fact (prompt content, via overlap between an attacker's guessed tokens and a victim's actual prompt). The channel we study operates at adapter management, not token-sequence caching, and leaks tenant identity, activity, and configuration — independent of what either party's prompt contains. We checked the closest defense proposal in this line of work directly rather than assume a gap: "Governing the KV Cache" (which surveys and mitigates PromptPeek/EarlyBird/InputSnatch-class attacks) scopes its own defense explicitly to cache-key computation at the infrastructure layer, and neither it nor the three attacks it surveys discusses adapter-management-layer channels — an absence of discussion, not a stated exclusion, which is the honest way to characterize a gap found in a single-author, one-month-old preprint rather than a comprehensive field survey. Our contribution is this instantiation and its consequences (§4), not the underlying cache-timing technique.

**Precision that matters for the threat model.** What an attacker directly measures is *residency* — whether an adapter occupies the cache right now. What they *want* to know is whether a tenant was *active*. These are not automatically the same fact, and collapsing them without comment would overstate the claim: an adapter could be resident because of stale, not current, activity, or because of another mechanism entirely. We therefore state the inferential step explicitly rather than assume it: under an LRU eviction policy — the default in the serving stack we study, and the common case in production multi-LoRA systems — recent residency is attributable to recent activity, and RQ2 demonstrates this attribution holds empirically, not just in principle.

**Who profits, concretely.** Residency tells an attacker *when* a co-tenant is active, not *what* they said — the "so what" needs a named adversary, not just "the channel exists." Our primary scenario is competitive business intelligence: a co-tenant on a shared platform (e.g., a competing business unit, or a competitor who has simply signed up as a paying customer of the same platform) infers another tenant's request volume and activity pattern over time — daily/weekly cadence, sudden spikes, sustained silence — without ever seeing a single prompt or output. This is the kind of signal that lets a competitor estimate a rival's customer traffic, product launch timing, or usage growth ahead of, say, a funding announcement, purely from cache-eviction timing on shared infrastructure neither party controls. A secondary scenario follows directly from the rank-leakage result (§4.3.1): adapter rank is deployment metadata that can correlate with a tenant's service tier, model size, or configuration choices — inferring it via timing is a form of configuration-IP disclosure, distinct from (and additive to) the activity-pattern leak.

**Contributions.** In one sentence: *we identify adapter residency as a new cross-tenant timing side channel in multi-LoRA LLM serving, distinct from prompt/prefix-cache side channels, and demonstrate that an unprivileged co-tenant can use this signal to infer victim activity — a result that survives even a competently configured platform — and, when adapter identifiers are additionally addressable, identify the active tenant.* We are not claiming the first timing side channel in LLM serving generally — that literature is active and growing — only a new architectural leakage surface within it, at the adapter-management layer rather than the prompt/token-cache layer. Concretely, we make five escalating empirical claims, each validated on a real, running multi-LoRA deployment (vLLM, Llama-3.2-1B, two adapters trained on genuine medical and legal Q&A content, RTX 4060 GPU) rather than a simulation:

1. **Existence (§4.1).** Adapter residency is externally observable from request timing alone, with near-perfect separability (AUC 0.92–1.00) between hot and evicted states.
2. **Inducibility (§4.2).** An attacker can *actively* manipulate residency — evicting a target adapter using only adapters they themselves control — and then detect the victim's subsequent activity via a prime-and-probe protocol (AUC 1.00).
3. **Survival under the obvious fix (§5.5), the paper's central claim.** Blocking cross-tenant adapter naming is the deployment fix a reviewer reaches for first, and we measure — rather than assume — whether the channel survives it. It does: an attacker who never names or probes the victim's adapter, only watches its own adapters for unexpected eviction, still detects victim activity at AUC=0.79-0.99 depending on a cache-sizing parameter operators do not currently treat as security-relevant. We treat this as the central claim because, unlike claim 4 below, it does not depend on any platform misconfiguration.
4. **Identification (§4.3), the channel's upper bound under one additional, avoidable condition.** If adapter identifiers *are* addressable across tenants — a real, well-documented misconfiguration (standard practitioner guidance derives adapter selection from the authenticated caller's own token), not a subtle one — probing multiple co-resident adapters independently lets an attacker name *which* tenant is active, not merely that some tenant is — 98.3% four-way classification accuracy across 120 trials — and, as a direct byproduct of the same measurements, reload latency leaks the victim adapter's *rank* (a configuration/size fingerprint), a statistically robust effect (p<10⁻⁶) we did not have to design a separate experiment to obtain.
5. **Control (§4.4).** We rule out the obvious alternative explanation — that the attacker is merely *interfering* with, not *observing*, the victim — by showing the channel is a pure information leak: under a batch-invariant serving configuration, we observe exact equality across all 300 compared token-level logprob positions (zero difference) regardless of attacker activity. We also show this claim is configuration-dependent: under default serving settings, concurrent load *does* measurably perturb outputs via known batching-numerics non-determinism, and we report this rather than only the configuration that supports the cleaner story.

Beyond these five claims, we characterize the channel's behavior under realistic contention rather than only on an idle GPU — the existence signal is recoverable under moderate contention, while severe contention can both overwhelm the activity-detection signal directly and invalidate fixed-threshold identification separately; adaptive detection remains an open robustness problem we identify a partially-validated fix for (§4.5) rather than leave unexplored.

## 2. Threat Model and System Model

**System model.** We study a multi-tenant LLM serving deployment in which one base model (Llama-3.2-1B) is shared by many tenants, each customizing it via a LoRA adapter. The serving engine (vLLM) maintains a two-tier adapter cache under LRU eviction: a small GPU-resident tier (`--max-loras`, holding 2 adapters in our configuration) and a larger CPU-resident tier (`--max-cpu-loras`, holding 4). An adapter not present in either tier must be reloaded from disk before it can serve a request. This tiered structure — a small GPU-resident working set backed by a larger, slower fallback — is not specific to our test configuration; multi-LoRA serving systems commonly employ hierarchical or tiered adapter management to avoid keeping every tenant's adapter GPU-resident, since that does not scale to realistic tenant counts. We study vLLM's specific two-tier (GPU/CPU) plus disk implementation; we do not claim every cited system (e.g., S-LoRA, LoRAX) implements this exact GPU→CPU→disk LRU hierarchy, only that the general pattern — a bounded fast tier with eviction to a slower fallback — is the common architectural response to the same scaling constraint, and is the specific mechanism this paper studies.

**Actors.** A *victim* tenant owns one or more adapters (we study two, `med` and `law`, trained on distinct real content domains) and issues ordinary inference requests to their own adapter(s). An *attacker* is simply another paying tenant of the same platform: it has no elevated privilege, no access to server logs, GPU metrics, scheduler state, or any other tenant's requests or outputs. The attacker also controls several adapters of its own ("junk" adapters in our experiments), used purely as cache-pressure tools, not as part of the observable signal.

**Attacker capability.** The attacker can (a) issue inference requests to adapters it controls, and (b) issue inference requests naming the specific victim adapter it wishes to probe, timing only the wall-clock latency of its own requests. Capability (b) — that a victim's adapter is addressable by name from an arbitrary tenant's API calls — is the assumption our identification result (RQ3) depends on, and we state it explicitly rather than leave it implicit: it holds in our test configuration, matching vLLM's default behavior where any caller may select any registered adapter by its served name, and it is realistic for deployment patterns where adapter identifiers are shared across a platform's tenant base (e.g., internal multi-team deployments, or marketplace-style platforms where fine-tuned models are addressable across accounts). It does *not* hold in deployments that gate adapter selection behind per-tenant authorization — the security-conscious default: standard practitioner guidance for multi-tenant platforms is that a resource identifier like an adapter name should be derived from the authenticated caller's own token, never accepted as attacker-suppliable input, which makes capability (b) a real but well-documented, avoidable misconfiguration rather than a subtle architectural trap. In that setting, the weaker existence/inducibility signal (RQ1–RQ2, whether *some* cache pressure exists) still leaks through contention effects on the attacker's own adapter's latency — we measure this directly rather than leave it hypothetical (§5.5) — but the strong identification claim (RQ3, *which* tenant) requires name-addressability. We therefore treat RQ3 as characterizing this channel's upper bound under one specific, checkable, and avoidable condition, not as the paper's central claim; §5.5's measured survival of the channel under the condition we expect a competently configured platform to actually be in is the central claim.

**Attacker knowledge.** The attacker knows the *existence* and *name* of the victim adapter(s) it targets (a reasonable assumption when adapter names correspond to known, discoverable tenants or products on a platform) but has no knowledge of, and never observes, the victim's prompts, outputs, or logprobs.

**Two deployment scenarios, and which claims survive each.** Because capability (b) above is load-bearing for the paper's central claim, we state its consequences as two explicit scenarios rather than one blended assumption:

- **Scenario A — adapter names are addressable across tenants** (matches our test configuration and platform patterns where adapter identifiers are shared across a tenant base, but is also a real, well-documented misconfiguration on any platform that fails to derive adapter selection from the authenticated caller's own token). All four RQ1-RQ4 results hold, including adapter-granular *identification* of which specific tenant is active — the channel's upper bound, conditioned on this specific, avoidable configuration state.
- **Scenario B — adapter selection is gated behind per-tenant authorization** (the victim's adapter cannot be named by an arbitrary caller; the condition we expect a competently configured platform to actually be in). The identification claim (RQ3) does **not** hold as demonstrated. A weaker residual signal survives: contention for the same shared, bounded cache (GPU/CPU tiers) still perturbs the *attacker's own* adapter's latency when a victim's activity forces evictions, giving an existence/activity-level signal ("someone is under load") without naming *which* tenant. We measure this channel directly (§5.5) rather than leave it as a plausible mechanism: on an idle GPU, AUC=0.79-0.99 depending on CPU-tier cache headroom — this, not Scenario A's identification result, is the paper's central claim, precisely because it requires no misconfiguration to hold. Under severe shared contention, however, this signal is not reliably established at the sample size we tested, and we do not have evidence that aggregation recovers it (§5.5) — an open robustness question, stated here rather than left for a reader to discover only after the claim above.

**Ground-truth discipline.** Throughout our experiments we maintain a strict separation between what the *attacker* observes (client-side request latency, timestamped, nothing else) and what the *experimenter* uses to label ground truth (server-side control over when a simulated victim request occurs). The detector under test is never given the ground-truth label directly, only the attacker's own timing measurements — matching the real attacker's actual epistemic position.

**Out of scope.** We do not build or evaluate a multi-replica / load-balanced production deployment; all experiments run on a single GPU, single serving process. §6 discusses the conditions (adapter-affinity routing) under which we expect the channel to persist in a multi-replica setting, and scopes full evaluation of that setting as future work.

## 3. Methodology

### 3.1 Infrastructure

All experiments run on a single consumer GPU (NVIDIA RTX 4060 Laptop, 8GB VRAM) via WSL2/Ubuntu 22.04, serving Llama-3.2-1B through vLLM 0.28.0 with `--enable-lora --max-loras 2 --max-cpu-loras 4 --max-lora-rank 32 --gpu-memory-utilization 0.75 --max-model-len 4096`. Two environment-level fixes were required for this configuration to run correctly under WSL2 and are reported here for reproducibility rather than treated as incidental: `VLLM_WSL2_ENABLE_PIN_MEMORY=1` (vLLM disables pinned-memory/UVA under WSL2 by default as a conservative measure; the WSL2 kernel used here, 6.6.114, is well above the version threshold at which pinned memory is actually supported) and `VLLM_USE_FLASHINFER_SAMPLER=0` (the default sampler JIT-compiles a kernel via `nvcc`, which is not present in a runtime-library-only CUDA install; this is orthogonal to the phenomenon under study, so we disable it rather than install a full CUDA toolkit).

**Which experiments use which configuration.** Most of this paper (RQ1-RQ4, the rank and cache-size sweeps, cross-model replication, Scenario B, and the defense evaluation) uses the single configuration above, with adapter files read over WSL2's 9p bridge to a Windows-hosted drive. Two later checks deliberately use a different configuration, and we flag this explicitly rather than let a reader infer it from scattered mentions: the filesystem-bridge robustness check (§3.7) and the production-scale cache check plus its 8-way identification extension (§4.6) both run on native ext4 storage, and the production-scale check additionally uses `--max-loras 8 --max-cpu-loras 64` instead of the values above. Every number in this paper states which configuration produced it; §3.7 discusses why cross-configuration absolute-scale comparisons are not meaningful, only within-configuration ones.

Two adapters carry the victim role: `med` (rank 8, LoRA on `{q,k,v,o}_proj`), trained for 12 epochs on 30 genuine medical Q&A pairs (train loss 1.74→0.37), and `law` (rank 32, same target modules), trained identically on 30 genuine legal Q&A pairs (train loss 1.58→0.34). Both were spot-checked post-training to confirm domain-correct completions (e.g., `med` correctly answers a diabetes-symptoms query; `law` correctly defines a contract) rather than assumed to have converged from loss curves alone. Six additional "junk" adapters (untrained, standard-LoRA-initialization stand-ins at ranks 8/16/32) serve as attacker-controlled eviction-pressure tools; because a LoRA adapter's reload cost is a function of its tensor shapes, not its trained content, untrained adapters are valid stand-ins for pure cache-pressure purposes (used in RQ1's initial characterization) while the victim-identity and content-dependent claims (RQ3 onward) use the real trained adapters exclusively.

### 3.2 Timing harness

The attacker's measurement primitive (`Prober`) sends a minimal completion request (`max_tokens=1`, `temperature=0`) to a named adapter and records wall-clock latency via `time.perf_counter_ns()`, alongside a GPU telemetry snapshot (temperature, SM/memory clock, utilization, power draw, via NVML) taken immediately before the request. Requesting only a single output token keeps latency dominated by (reload cost, if any) plus prefill, rather than variable decode-length noise. GPU temperature/clock logging is not a formality: because the test GPU is a laptop part, thermal throttling is a real, physically plausible confound for any latency-based claim, and we report the observed thermal range alongside every core result specifically to rule it out (RQ1: 53–55°C, effectively flat, across the idle-GPU run).

### 3.3 Per-RQ protocols

**RQ1 (existence).** For each of 30 trials, we force each of three residency states in turn and measure the immediately following probe: *hot* (probe target twice, use the second reading); *RAM-evicted* (probe target, then probe `max_loras` distinct filler adapters to push target out of the GPU tier only, probe target again); *disk-evicted* (probe target, then probe `max_cpu_loras + 1` filler adapters — cycling through the filler set if necessary — to push target out of both tiers, probe target again).

**RQ2 (inducibility).** Per trial, we prime by disk-evicting the target (as above), then flip a ground-truth label — balanced, not coin-flipped, alternating `active`/`idle` across trials — hidden from the detector. If `active`, we issue one additional, experimenter-only request to the target (simulating the victim's own traffic; its latency is recorded but never given to the detector) and wait a fixed gap (0.3s). The attacker's *only* signal is one subsequent probe of the target, classified `active` if latency falls below a threshold calibrated from RQ1's idle-GPU gap, else `idle`.

**RQ3 (identification).** Per trial, we evict two named target adapters (`med`=A, `law`=B, double-pass eviction to guarantee both clear both cache tiers even though they compete for the same two GPU-tier slots), then flip a ground-truth label cycling through four balanced classes (`A`, `B`, `both`, `neither`). Depending on the label, we issue 0, 1, or 2 hidden experimenter-only activity requests, then the attacker burst-probes both A and B, in order, and classifies each independently against the threshold, combining the two binary calls into the four-way label.

**RQ4 (control).** Ten fixed prompts (five per adapter, novel — not drawn from the training set) are completed under greedy decoding (`temperature=0`) with top-5 logprobs requested, once with no concurrent traffic (`absent`) and once with a 6-worker concurrent noise load active (`present`). We compare generated text for exact match and compare every returned token-position logprob for exact numerical equality, under two server configurations: default, and with `VLLM_BATCH_INVARIANT=1`.

### 3.4 Noise-robustness protocol

To avoid reporting only idle-GPU best-case numbers, we built a concurrent load generator: several worker threads continuously firing randomized-adapter, randomized-prompt-length, randomized-generation-length requests at the server, run alongside the RQ1–RQ4 protocols above. The generator excludes all target/canary adapters from its own traffic pool — an early version did not, which accidentally reloaded the target adapter mid-trial and contaminated the `idle` ground-truth label; every noise-robustness result in §4.5 uses the corrected generator.

### 3.5 Adaptive-threshold refinement

Because a fixed detection threshold (calibrated on idle-GPU latency) is, by construction, vulnerable to breaking down when the true latency distribution shifts under load, we additionally tested a paired-baseline detector: each target probe is accompanied by a probe of a *canary* adapter — a third adapter, excluded from both the noise pool and the eviction-filler set, kept independently resident — and classification is based on the *difference* between target and canary latency rather than an absolute value, on the reasoning that shared queueing delay should cancel out of a difference between two temporally-proximate measurements. We tested two dispatch strategies: *sequential* (probe canary, await its response, then probe target) and *concurrent* (fire both as simultaneous requests via a thread pool, diffing their independent completion latencies). Results for both are reported in §4.5, including where this refinement succeeded and where it did not fully resolve the underlying problem.

### 3.6 Statistical methodology

Every reported proportion (accuracy) carries two independently-computed 95% confidence intervals: a nonparametric bootstrap (10,000 resamples) and a Wilson score interval (the standard closed-form method for binomial proportions), rather than a single, less-scrutinized estimate. Every reported AUC carries a bootstrap CI computed the same way. Before applying any parametric test (Welch's t-test) to a latency comparison, we verify the normality assumption via Shapiro–Wilk rather than assume it — latency distributions are frequently right-skewed, and in our data several key distributions (disk-evicted latency, both adapters' evicted-latency distributions used for the rank-leakage claim) are confirmed non-normal (p<0.02). Where normality fails, we report the nonparametric Mann-Whitney U test alongside the t-test, plus its associated rank-biserial correlation as a nonparametric companion to Cohen's d. Where multiple related comparisons are drawn from one dataset (RQ1's three pairwise state comparisons), we note the Bonferroni-corrected significance threshold explicitly and confirm no conclusion changes under it.

### 3.7 Measurement validity: absolute-scale drift and why it does not affect our conclusions

Absolute latency values differ across the runs reported in this paper: idle-GPU RQ1 baseline (§4.1) puts disk-eviction reload at 80.53ms; a later run of the same rank-8 adapter under RQ3's protocol (§4.3.1) reads 83.37ms; the same adapter again under the rank-sweep protocol (§4.6) reads 99.52ms; RQ2's idle-condition probe (§4.2) averages 104.00ms; the Poisson-traffic experiment's idle condition (§4.6) averages 228.8ms.

**Causes, confirmed by direct instrumentation:** (1) substantial cumulative GPU thermal/power throttling across this project's many-hours span (`nvidia-smi -q -d CLOCK,PERFORMANCE`); (2) adapter files read via WSL2's 9p filesystem bridge to a Windows-hosted drive (`df -T`), slower and more variable than native ext4; (3) one proxy implementation used a non-pooled HTTP client that accumulated connection overhead over long sessions (fixed, §5.6); (4) session-length effects (§4.6, §5.6) consistent with, but not proven to be, further consequences of (1)-(3).

**Why this does not undermine the paper's conclusions.** Every comparison this paper's claims rest on is *within-run* and *threshold-free*: AUC and distinguishing advantage are computed by rank-ordering latencies measured under the same run's conditions against each other, not against a value carried over from a different run or a different day. A uniform shift in the absolute scale of a run — the entire failure mode identified above — cancels out of a within-run rank statistic; it would only threaten a conclusion that compared an absolute latency value from one run against a fixed threshold calibrated on a different run, which is precisely the failure mode diagnosed and corrected in §5.5-§5.6 (a single-shot threshold trained on one run's scale, applied to another). Cross-run comparisons in this paper (e.g., Table 6, cross-model latencies in §4.6) are used to establish *ordering and proportionality* (does latency scale with rank/model size in the expected direction), not to claim two absolute numbers from different sessions are the same measurement.

**Canary protocol, adopted after diagnosing the causes above, not from the start of this project:** a fixed block of repeated hot-adapter probes, logged at the start and end of every experiment run, makes environment stability a number in the log rather than an inference. Used for every run from §4.6's production-scale checks onward; not present for earlier results.

**A dedicated robustness check: does the disk-tier gap survive removing the 9p bridge?** We re-ran RQ1's exact protocol (target `med`, the same six filler adapters, `--max-loras 2 --max-cpu-loras 4`) on a fresh vLLM instance serving adapters from native ext4 (`/home/researcher`) instead of the 9p bridge to a Windows-hosted drive that every other result in this paper uses, with the GPU confirmed at its full rated power budget to isolate the filesystem variable specifically. At n=100: hot mean=29.32ms (std=10.64), ram_evicted mean=35.00ms (std=8.16), disk_evicted mean=40.65ms (std=9.04) — compare to Table 1's 27.13/36.58/80.53ms. `hot` and `ram_evicted`, whose reload paths never touch the filesystem (GPU-resident and CPU-RAM-resident respectively), are statistically indistinguishable in absolute scale between the two environments; `disk_evicted`, the one state whose reload reads the adapter's tensor file from storage, drops by roughly half (80.53ms → 40.65ms). This is mechanistically exactly what a 9p-bridge confound predicts, and it is real: **most of Table 1's disk-eviction gap magnitude, though not its existence, was 9p-bridge overhead specific to the one residency state that performs a disk read.**

Single-probe separability on native storage is correspondingly weaker than Table 1 reports: AUC=0.8667 [0.8053,0.9219] (hot-vs-disk), 0.7432 [0.6704,0.8098] (ram-vs-disk), 0.7937 [0.7212,0.8594] (hot-vs-ram) — all non-normal by Shapiro-Wilk (p<0.0001), all significant by Mann-Whitney U (p<10⁻⁸), but far from Table 1's near-perfect separation. Applying the same aggregation strategy §4.5 already establishes for contention noise — median-of-N repeated probes — recovers strong separability here too: median-of-5 restores hot-vs-disk AUC to 0.9950 [0.9770,1.0000]. **The qualitative claim (adapter residency is externally observable, ordered hot<ram<disk, via timing alone) replicates on native storage; the near-perfect single-probe AUC this paper otherwise reports throughout §4 is partly a 9p-bridge artifact.**

**A second, more severe instance of the same confound: the rank-leakage slope.** We ran the same native-storage check on §4.6's rank sweep (same five adapters, same protocol, n=15/rank). The 9p-bridged slope (3.42ms/rank-unit, R²=0.967) drops to **0.14ms/rank-unit [0.10, 0.17], R²=0.47** on native storage — about 1/25th, a substantially larger inflation factor than the roughly 2x seen on the disk-tier gap itself. This is not a separate, unrelated finding: rank differences are file-size differences, and a filesystem bridge whose overhead scales with bytes transferred amplifies a size-scaling effect (rank) far more than it inflates a single fixed reload cost (residency state) — the same underlying mechanism, more visible here because this measurement is sensitive to a *derivative* (how fast latency grows with size), which a per-byte bridge overhead distorts more than an intercept. The relationship remains real, monotonic, and significant (p=1.5×10⁻¹¹) on native storage — only its magnitude was overstated. We treat the native slope as the trustworthy number throughout the paper.

We did not re-run RQ2-RQ4, the cache-size sweep, cross-model replication, Scenario B, or the defense evaluation on native storage — doing so for every result in this paper was not feasible in the time available — so those results' absolute latency scale should be read as measured (9p-bridged) and internally consistent with each other (the within-run invariant above still applies), but likely inflated in the same disk-tier-specific way both checks above quantify, and possibly more severely for any result whose claim is about a *rate of change* (like rank leakage) rather than a fixed-state comparison (like hot-vs-evicted).

### 4.2 RQ2 — Inducibility

Using prime-and-probe (§3.3) with `med` as the target and a hidden, hidden-from-detector ground-truth activity label, the attacker's single-probe detection AUC is 1.0000 (threshold-free), replicated identically using both a placeholder stub adapter (n=40) and the real trained `med` adapter (n=40). Mean probe latency was 42.78ms (std 6.57) for `active` trials and 104.00ms (std 10.44) for `idle` trials; the two distributions do not overlap (max active = 57.61ms, min idle = 88.80ms), so any threshold in [58, 88]ms achieves 40/40 raw accuracy — a fixed 50ms threshold, chosen a priori from RQ1's numbers rather than tuned on this data, achieved 39/40 (97.5%), the one miss attributable purely to that threshold choice rather than a genuine ambiguity in the underlying signal.

### 4.3 RQ3 — Identification (the channel's upper bound under adapter-name addressability)

Independently burst-probing two named, co-resident adapters (`med`=A, `law`=B) after evicting both, across four balanced ground-truth classes (A active / B active / both / neither), achieved **98.33% four-way classification accuracy (118/120 trials)** at n=120 (30/class), using the real trained `med`/`law` adapters. Table 2 gives the confusion matrix.

**Table 2. RQ3 confusion matrix, n=120 (rows = ground truth, columns = predicted).**

| | A | B | both | neither |
|---|---|---|---|---|
| **A** | 30 | 0 | 0 | 0 |
| **B** | 0 | 28 | 0 | 2 |
| **both** | 0 | 0 | 30 | 0 |

Both errors are the same specific failure mode — `B` misclassified as `neither` — rather than noise scattered across classes; per-class F1 is 1.0000 for A/both/neither and 0.9655 for B. We report a genuine, small, characterized error rate rather than a suspicious "always perfect" score: accuracy 95% CIs are [95.83%, 100.00%] (bootstrap, 10,000 resamples) and [94.13%, 99.54%] (Wilson score). An earlier n=40 stub-adapter pilot and n=60 real-adapter run both scored 100% (40/40, 60/60); the two additional errors surfacing only at n=120 illustrate why we escalated sample size specifically to move past the point where a perfect small-sample score could be mistaken for a truly error-free channel.

**Empirical information rate.** From n=60 real-adapter timestamps, average wall-clock time per trial was 1.255s, giving 2.00 bits of tenant-identity information (4 balanced classes, near-zero error) per trial at **≈1.6 bits/s**, or **≈7 attacker requests per bit** of identity information. We do not compare this against prior LLM-serving timing attacks' reported measurement counts: those recover high-entropy prompt content, this recovers 2 bits from a known 4-way alphabet, and requests-per-bit is not comparable across targets of different entropy — this is an efficiency figure for this specific inference task, not a superiority claim over a different one. We use "empirical information rate" rather than "channel capacity" deliberately: this is an observed throughput under our specific measurement protocol, not a capacity bound derived from a formally specified channel/noise model, and should not be read as the latter.

### 4.3.1 Adapter Configuration Leakage (a supporting observation)

As a byproduct of the same measurements behind RQ3, not a separately designed experiment, reload latency also correlates with adapter rank — configuration/size metadata distinct from tenant identity. §4.6's dedicated rank sweep (same content domain across five ranks, isolating rank from the content-domain confound an early two-point `med`-vs-`law` comparison could not) gives the trustworthy numbers, measured on native storage after §3.7 found the first, 9p-bridged measurement of this same sweep was inflated ~25x: slope 0.14ms/rank-unit, R²=0.47. At this magnitude the leak is coarse, not fine-grained — §4.6 gives the specific rank pairs that are and are not resolvable, and at what probe cost. We report this as a supporting observation rather than a headline claim: the effect is real and mechanistically expected (larger rank means a larger serialized adapter, and more bytes take measurably longer to read from disk), but substantially weaker than our first, 9p-inflated measurement suggested.

### 4.4 RQ4 — Control

We use this experiment as a control to isolate our timing channel from a separate, already-known confound — not as a novel finding about batching non-determinism itself. That batch composition can affect floating-point reduction order, and thus generation outputs under concurrent load, is a documented phenomenon in LLM serving (it is precisely why vLLM ships a named `VLLM_BATCH_INVARIANT` configuration option in the first place — the mitigation already existed before this paper). What we newly establish is narrower and specific to our setting: whether *our* attacker's presence measurably perturbs *this* victim's outputs, and whether enabling the existing mitigation is sufficient to rule that out for our channel specifically.

Comparing greedy-decoded completions and their logprobs across ten fixed prompts, attacker-absent vs. attacker-present (6-worker concurrent load), under two server configurations:

**Table 3. RQ4 output comparison.**

| Configuration | Text mismatches | Logprob diff (mean / max) | All-zero? |
|---|---|---|---|
| Default vLLM | 3/10 | 0.058 / 1.43 | No |
| `VLLM_BATCH_INVARIANT=1` | 0/10 | 0.0 / 0.0 | **Yes — all 300 compared positions** |

Under default settings, the naive claim that the channel is a "pure" leak with zero output effect is **false**: concurrent load measurably perturbs generation via known batching-numerics non-determinism (different batch composition → different floating-point reduction order → occasional argmax flips at greedy decoding), and we report this rather than the more convenient alternative. With batch-invariant kernels enabled, the same comparison yields **exact** equality — not "statistically indistinguishable," but zero difference — across all 300 compared token-level logprob positions. Under this configuration, we isolate the timing channel from batch-dependent numerical variation: the identity/residency leak is demonstrated free of any confounding output effect. We do not claim this generalizes to every possible serving configuration — only that batch-invariant kernels are sufficient to rule out this specific confound, and default-configuration behavior (which does not rule it out) is reported alongside it rather than omitted.

### 4.5 Noise-robustness matrix

All results above are measured on an idle GPU; we separately tested 6-worker concurrent contention (randomized adapter/prompt/generation length, target and canary adapters excluded from the noise pool).

**The bound: existence survives contention and recovers cheaply via aggregation; fixed-threshold identification does not, and the cause is calibration, not a vanished signal.** Single-probe AUC drops under heavy contention (hot-vs-disk 1.00→0.70, hot-vs-ram 0.92→0.68, ram-vs-disk 1.00→0.48), but median-of-3 probes restores hot-vs-disk to AUC=1.0000, while hot-vs-ram plateaus at ~0.68-0.70 regardless of averaging and ram-vs-disk worsens (0.67→0.53) — build the attack around the disk-eviction tier under contention, not the finer which-tier distinction. (This recommendation is scoped to the small-scale, 9p-bridged configuration tested here; §3.7 and §4.6 both found the RAM tier can separate comparably or better once the 9p-bridge inflation of the disk tier is removed — untested under contention, §8.) Under severe contention, derived activity/identification tasks become substantially less reliable, but for two different reasons, not one: RQ2's single-event activity signal (AUC drops to 0.45-0.50) is overwhelmed by queueing noise directly — the reload-cost signal is genuinely smaller than the noise scale here, and it does not recover with median-of-N aggregation. RQ3's four-way identification (accuracy 25-30%) fails differently: its fixed absolute threshold, calibrated on idle-GPU numbers, becomes miscalibrated as the latency scale inflates 10-40x under this load. Scenario B is evaluated separately, under its own contention test, in §5.5. A paired-canary (concurrent-dispatch) detector partially fixes this — cancelling shared queueing delay collapses diff magnitude ~10-20x — but a single global threshold still fails across a run whose ambient load itself drifts; a rolling/windowed threshold is the identified, not-yet-implemented fix (§8).

### 4.6 Generalization: rank/cache-size sweeps, a second base model, and realistic victim traffic

The results above establish the mechanism on one configuration (Llama-3.2-1B, `max_loras=2`) with a two-point rank comparison (r8 vs. r32, confounded with content domain) and one deterministic form of "victim activity." We address each of these scoping limitations directly.

**Rank sweep (isolating rank from content domain), measured on native storage.** We trained four additional adapters at ranks 1, 16, 32, and 64, all on the *same* content domain (`med`) as the existing rank-8 `med` adapter, to isolate rank as the only varying factor. The first measurement of this sweep ran over the 9p bridge, like every other result in §4.1-§4.5; §3.7 found this inflated the slope by ~25x, the most severe instance of the filesystem-bridge confound in this paper, so we report the native-storage re-measurement as the primary result here rather than presenting the discredited number in a table and the correction in prose.

**Table 4. Reload latency vs. LoRA rank, same content domain, native ext4 (n=15/rank) — the trustworthy measurement.**

| Rank | Mean (ms) | Std |
|---|---|---|
| 1 | 31.64 | 3.77 |
| 8 | 32.48 | 3.46 |
| 16 | 33.73 | 4.00 |
| 32 | 35.87 | 2.70 |
| 64 | 40.19 | 2.82 |

Linear fit: slope=**0.1364ms/rank-unit [0.1023, 0.1704]**, R²=**0.4661**, p=1.5×10⁻¹¹. A log-linear fit gives R²=0.3376 — we checked, rather than assumed, whether linear still wins at this reduced R², and it does (a 0.13 gap, not noise), consistent with the physical expectation that a LoRA adapter's serialized size scales linearly with rank. The relationship is real, monotonic, and significant; it is far noisier than our first measurement suggested. **The 9p-bridged version of this same sweep** (rank 1/8/16/32/64 means 66.63/99.52/131.15/183.60/286.32ms, slope=3.42ms/rank-unit [3.27,3.57], R²=0.967) is a ~25x inflation, mechanistically consistent with §3.7: rank differences are file-size differences, and a bridge whose overhead scales with bytes transferred amplifies a size-scaling slope far more than it inflates one fixed reload cost. We treat the table above as the trustworthy measurement throughout this paper.

**What this leaks in practice: coarse buckets, not fine distinctions.** At native magnitude, adjacent or near ranks are not reliably separable even with substantial aggregation: rank 8-vs-16 (a 1.25ms gap) sits at single-probe AUC=0.61 and does not reach AUC≥0.95 within 30 median-aggregated probes; rank 16-vs-32 (2.13ms) needs ~20. Wider spans are cheap: rank 8-vs-32 (3.39ms) needs ~10 probes, rank 32-vs-64 (4.33ms) needs ~5, and rank 8-vs-64 (7.72ms) and 1-vs-64 (8.56ms) both already reach AUC≥0.95 with a single probe. An attacker can cheaply distinguish a "small" from a "large" adapter tier but cannot cheaply distinguish adjacent rank values — the honest and more useful version of "rank leaks via timing" than a single slope number conveys.

**Cache-size sweep.** We re-ran the core RQ1 hot-vs-disk-evicted measurement at `max_loras`∈{1, 4} (in addition to the `max_loras=2` configuration used throughout the rest of the paper), holding `max_cpu_loras=4` fixed, to confirm the mechanism is not an artifact of one specific cache-size setting:

| 1 | 32.47 | 80.12 | 1.0000 |
| 2 (used throughout) | 27.13 | 80.53 | 1.0000 |
| 4 | 41.11 | 92.58 | 1.0000 |

The hot-vs-disk-evicted signal is perfectly separable at every tested cache size. **Production-scale cache configuration.** The sweeps above hold `max_cpu_loras=4` fixed; none test the cache size a real deployment would actually run. vLLM's own default for `max_cpu_loras` is `max_num_seqs` — commonly tens to hundreds of concurrent sequences in production, nothing like this paper's `--max-cpu-loras 4` — and at that scale, forcing an adapter to the disk tier requires an attacker to cycle `max_cpu_loras+1` distinct adapters rather than the 5 this paper otherwise uses. We tested this directly rather than leave it a hypothetical: a fresh server (native ext4, §3.7) registered 67 adapters (`med`, `law`, 65 filler adapters) at `--max-loras 8 --max-cpu-loras 64`, and both RQ1's and RQ3's protocols were re-run forcing full disk eviction through all 65 fillers.

| | Small-scale (this paper's default, §4.1/§4.3) | Production-scale (`8`/`64`) |
|---|---|---|
| hot mean (ms) | 27.13 | 20.73 (std 1.23) |
| ram_evicted mean (ms) | 36.58 | 28.27 (std 1.90) |
| disk_evicted mean (ms) | 80.53 | 33.57 (std 2.23) |
| RQ1 AUC hot-vs-ram | 0.9222 | **0.9944** [0.978, 1.000] |
| RQ1 AUC hot-vs-disk | 1.0000 | **1.0000** [1.000, 1.000] |
| RQ1 AUC ram-vs-disk | 1.0000 | **0.9689** [0.917, 1.000] |
| RQ3 4-way accuracy | 98.3% (n=120) | **90.0%** (36/40) |

At production cache scale, under an idle GPU, the existence signal (RQ1) does not weaken — every comparison remains near-perfectly separable, matching or exceeding the small-scale numbers, likely helped by this run's cleaner native-storage, stable-power conditions (§3.7). Identification (RQ3) drops from 98.3% to 90.0% at a single a-priori threshold (27ms, the midpoint of this run's own hot/disk means) giving **82.5%** (33/40, the honest, not-tuned-on-this-data number); per-adapter Youden-optimal thresholds — train-set-optimistic, as in §5.5 — recover 90.0% (36/40), with AUC=0.96 (`A`-active) and 1.00 (`B`-active) on the two underlying binary sub-tasks. Errors concentrate in one specific confusion (`both`→`B`, 3/10 `both` trials) rather than scattering across classes, the same pattern the small-scale run showed (`B`→`neither`, 2/30) — consistent with threshold calibration, not a vanished signal.

This directly answers the production-cache-size objection: disk-tier eviction is not eliminated at realistic cache scale, only made proportionally more expensive to induce (65 adapters to cycle, not 5) — a cost the attacker pays in requests, not in a newly-required capability, since Scenario A already assumes the attacker can register and address adapters it controls. We did not test this configuration under contention — §4.5's noise-robustness matrix used the small-scale config — so whether the production-scale signal is equally robust to concurrent load is untested, stated as a limitation (§8) rather than assumed.

**Identification beyond four classes: does accuracy hold, or does probe cost quietly buy it back?** RQ3 above tracks two named adapters (four classes). We extended this to eight independently-tracked, named adapters (`med`, `law`, and six further distinct adapters) at the same production cache scale, asking a direct single-label question — *which one* of the eight was active — rather than the four-class subset-combination design: per trial, all eight are forced to disk-evicted, one is hidden-touched as ground truth, and the attacker burst-probes all eight, predicting whichever came back fastest. This raises attacker probe cost linearly (8 probes/trial instead of 2) without any threshold to calibrate — argmin over 8 raw latencies is threshold-free by construction. Result, n=80 (10/class): **100% accuracy (80/80), 95% Wilson CI [95.4%, 100%]** — the true adapter consistently read 19-22ms against 7 others at 29-43ms, a gap wide enough that no trial was ambiguous. Probe cost compounds linearly with tracked-set size, as the critique anticipated; classification accuracy, at this sample size and this scale, does not degrade at all. **This is not a strictly harder task than the four-way design, and the 100% vs. 90.0%/82.5% comparison should not be read as "identification gets easier at scale."** Single-label argmin-of-8 has no calibration step at all — exactly where both four-way runs' errors came from (a per-adapter threshold, chosen a priori or Youden-recalibrated, that individual readings can cross). The realistic attacker task this experiment does not capture is *multi-label*: any subset of the eight tenants may be active simultaneously, not exactly one, giving 2⁸=256 possible ground-truth states rather than 8, and requiring the same per-adapter absolute thresholding the four-way design uses (and where its errors concentrate) rather than a threshold-free argmin. We did not push past 8 classes, n=80, or the single-label design, and note all three as the natural next step rather than claim this generalizes to arbitrarily large or multi-label tracked sets.

**Realistic (Poisson-process) victim traffic.** The RQ2/RQ3 protocols above use a deterministic, single, experimenter-inserted "victim request" as ground truth for "active." To test whether detection generalizes to actual stochastic tenant traffic, we replaced this with a background thread generating genuine Poisson-arrival requests to the target over a 3-second observation window, under four regimes: `idle` (no arrivals), `low` (rate 0.3 req/s), `high` (rate 2.0 req/s), and `bursty` (rate 2.0 req/s, all arrivals compressed into the window's first third) — the attacker takes a single probe at the window's end and must infer whether real victim traffic occurred during the window, from that one measurement.

This experiment surfaced two implementation issues worth reporting for other researchers building similar harnesses, both diagnosed and fixed rather than worked around silently. First, an early multi-probe-per-window design (8 probes spread across the window) produced a self-contamination artifact: the attacker's *own* first probe reloads the target, so every subsequent probe in the same window reads "hot" regardless of victim activity — 10/10 `idle` trials were misclassified as active, while all 30 active-regime trials were correctly detected, a clean signature of the attacker's own measurement sustaining the very state it is trying to observe. We corrected this to a single probe per window. Second, the background victim-traffic thread's arrival-interval sampling (`random.expovariate`) combined with a cooperative stop-flag checked only *after* each sleep meant a thread could sleep past its own window's end and continue firing requests into *subsequent* trials before terminating — `thread.join(timeout=2.0)` does not kill a thread, it only stops waiting for it. We fixed this with a interruptible-sleep pattern (checking the stop flag in short, bounded increments) so victim threads reliably terminate within their own window.

With both fixes applied, a *fixed* detection threshold (calibrated earlier in the session) no longer matched the absolute latency scale — plausibly cumulative session-level drift after several hours of continuous GPU activity, an artifact we note rather than paper over — but the underlying *rank-ordering* signal, evaluated via threshold-free AUC, was strong: idle-vs-low AUC=1.0000, idle-vs-high AUC=1.0000, idle-vs-bursty AUC=0.9600 (idle mean latency 228.8ms vs. 93–127ms for the three active regimes, n=10/regime). This is stronger evidence than the original deterministic-request design: the channel reliably distinguishes genuine, stochastic, realistically-shaped victim traffic from silence, not merely the presence of one artificially-inserted request. The practical lesson — reported honestly because it will recur in similar harnesses — is that fixed-threshold detectors need periodic recalibration or threshold-free (rank-based) scoring across long-running sessions where ambient conditions drift; this is the same underlying lesson as the noise-robustness matrix's severe-load finding (§4.5), now observed on a different, slower timescale.

**Volume, not just presence: does detection frequency track request rate?** §1's motivating scenario is a competitor inferring a rival's *traffic volume*, not merely whether traffic exists at all. We tested this directly at the production cache scale (§4.6 above): six victim request rates (0, 0.1, 0.3, 0.5, 1.0, 2.0 req/s, Poisson arrivals over a 3-second window, target `med` named directly), 15 trials/rate.

A first attempt ran the six rate conditions in ascending blocked order (all 15 trials at one rate, then the next) — we checked, rather than assumed, whether this was safe given the session-length drift documented above and in §4.5, and it was not: session-order and rate were nearly collinear (Spearman ρ=-0.603 for session-order-vs-latency against ρ=-0.592 for rate-vs-latency), meaning that run's apparent rate-tracking could equally have been generic drift. We discarded it as non-evidentiary rather than report it.

The corrected run randomizes (rate, trial) order per trial (seeded shuffle) and logs a 10-probe canary block of a non-target, non-filler adapter at the start and end of the session, so drift is a checked number rather than an assumption: settled canary latency was statistically indistinguishable start-to-end (18.04ms vs. 18.06ms, Mann-Whitney p=0.70), and session-order showed no residual association with either rate (ρ=-0.07, p=0.51, confirming the shuffle) or latency (ρ=0.09, p=0.37, confirming no drift this time).

With the confound ruled out, detection frequency by rate (Wilson 95% CI, n=15/rate) is:

| Rate (req/s) | 0 (idle) | 0.1 | 0.3 | 0.5 | 1.0 | 2.0 |
|---|---|---|---|---|---|---|
| Detected active | 6.7% | 73.3% | 73.3% | 80.0% | 86.7% | 100.0% |
| Wilson 95% CI | [1.2%, 29.8%] | [48.0%, 89.1%] | [48.0%, 89.1%] | [54.8%, 93.0%] | [62.1%, 96.3%] | [79.6%, 100.0%] |

Rate=0's 6.7% (1/15) is this detector's **false-positive rate**, not just the first point on a curve. Across all 90 trials, rate correlates strongly with both detection and raw latency (Spearman ρ=0.5466, p=2.5×10⁻⁸ for rate vs. detected-activity; ρ=-0.6232, p=5.4×10⁻¹¹ for rate vs. raw latency, threshold-free) — but a 20x span sits in the five nonzero rates, and three of those five detection-frequency points fall within 13 points of each other, so we checked directly rather than let the full-sample statistic imply more than it does. **Recomputing on the 75 nonzero-rate trials alone**: rate vs. detected-activity drops to ρ=0.2491 (p=0.031, barely significant), while rate vs. raw latency holds up meaningfully better at ρ=-0.4290 (p=0.00012). Most of the full-sample correlation is the idle-vs-any-traffic step, not a graded response across traffic levels — but a real, if modest, gradient among nonzero rates survives in the threshold-free measure, more clearly than in the binary detection call.

**The honest scope of this result:** strong presence/absence detection (a 6.7% false-positive rate against 73-100% detection once any victim traffic exists) plus a real but modest rate gradient within the nonzero range, visible mainly in raw latency rather than a fixed detection threshold. Saturation at rate=2.0 (100%) reflects the adapter becoming effectively continuously resident at that traffic level — mechanism, not a ceiling on sensitivity. This directly supports §1's motivating scenario under Scenario A (the victim adapter is named directly, as throughout most of this paper): the channel *tracks* victim request rate, in an ordinal, ρ-quantified sense — we do not claim it *estimates* rate, which would require a held-out inversion of the curve we have not built. A Scenario-B-specific version of this sweep (self-eviction-only, per §5.5) remains open (§8).

## 5. Security Analysis

The threat model (§2) states the attacker's position; this section makes the operational picture precise — what the attacker must actually be able to do, what the attack costs, where it applies in real deployments, and what a defender can do about it.

### 5.1 Attacker capabilities and assumptions, enumerated

An attacker mounting the full RQ1→RQ3 chain requires exactly the following, no more:

1. **An ordinary API credential** on the shared platform — the same access tier as any paying customer, not an elevated or operator role.
2. **The ability to select a small number of adapters it controls** ("junk" adapters in our experiments) — these can be low-effort, near-zero-cost adapters (untrained stand-ins suffice, §3.1), since only their tensor *shape*, not their trained content, matters for cache-pressure purposes.
3. **The ability to name the victim adapter(s) it targets** in its own requests (Scenario A, §2) — this is the one capability that does not hold universally, and, per standard practitioner guidance, should not hold on a well-configured platform. The attack's identification claim (RQ3) is void without it; §2 and §5.5 measure what survives when it doesn't (AUC=0.79-0.99), which we treat as the paper's central claim, not a fallback.
4. **Wall-clock timing of its own requests only.** No server-side telemetry, no logs, no side information beyond what any API consumer already receives (a response and its arrival time).

No assumption is made about the attacker's knowledge of *when* a victim is likely to be active, the victim's request rate, or the platform's current load — the attack is designed to work from timing alone, and §4.5–4.6 report where that assumption's limits are (severe contention, threshold drift over long sessions).

### 5.2 Attack prerequisites, concretely

Mounting the attack in a real deployment requires, in order: (1) confirming the platform's adapter cache is bounded and shared across tenants (true of any multi-LoRA serving system built for realistic tenant counts, §1) — this is often discoverable simply by observing that a first request to a rarely-used adapter is measurably slower than a repeated one; (2) registering or otherwise controlling enough distinct adapters to reliably force eviction of a target — `max_cpu_loras + 1` for full disk eviction (5 at this paper's small-scale config, 65 at the production-scale config we test in §4.6), or only `max_loras` (8 at production scale) if the weaker RAM-tier signal suffices, which §4.6's production-scale numbers suggest it may; (3) identifying the victim adapter's name — either because names are public product/tenant identifiers on the platform, or through auxiliary reconnaissance out of scope for this paper; (4) running the prime-and-probe protocol (§3.3), which is entirely request/response traffic indistinguishable, at the individual-request level, from ordinary API usage.

### 5.3 Practical deployment scenarios

Scenario A (§2) — where this paper's identification upper bound (RQ3) applies in full, conditioned on the misconfiguration described in §2 — plausibly matches: internal multi-team or multi-product deployments where different business units' fine-tuned models share infrastructure and are addressed by a common internal naming scheme; marketplace-style platforms where fine-tuned/customized models from different accounts are browsable and invocable by any platform user (by design, for discovery); and any deployment that exposes a `--lora-modules`-style flat namespace to its full API surface without per-adapter access control, which is vLLM's and several other systems' default posture unless explicitly configured otherwise. Scenario B — where the measured existence/contention signal (§5.5, AUC=0.79-0.99) is what survives, and which we treat as this paper's central claim — matches any platform that follows standard practitioner guidance on adapter-selection authorization; we expect this is the common case for security-conscious commercial multi-tenant offerings, though we have not attempted to quantify the prevalence of either scenario across real deployments.

### 5.4 Mitigations and their tradeoffs

We measure two of the mitigations below directly (§5.5, §5.6) and discuss the remainder without experimental evaluation, marking each accordingly rather than presenting all of them at the same confidence level.

- **Per-tenant adapter namespace isolation** (do not allow tenant B to name tenant A's adapter). Directly closes Scenario A and voids RQ3's identification claim as demonstrated. Does not, by itself, address RQ1/RQ2-style existence/activity signals if the attacker's *own* adapter's latency is still perturbed by shared-cache contention from other tenants' activity (the Scenario B channel, measured in §5.5 at AUC=0.79-0.99) — namespace isolation is necessary but not sufficient on its own.
- **Per-tenant dedicated cache slots** (no cross-tenant sharing of the GPU/CPU adapter tiers at all). This eliminates the channel completely, at every RQ, because it removes the shared resource the entire mechanism depends on — but it also eliminates the efficiency gain that motivates a *shared* multi-LoRA cache in the first place (§1). This is the fundamental tension our results expose: the same design decision that makes multi-tenant LoRA serving efficient is the one that makes it observable, and a platform operator faces a real efficiency/isolation tradeoff here, not a free fix.
- **Constant-time (padded) adapter loading** — the classic side-channel defense. **Measured, not just discussed** (§5.6), and the measurement surfaced two real analysis/implementation errors along the way (both corrected in-place, see §5.6 for the full account). At n=200, T_MAX=150ms: hot-vs-ram_evicted and hot-vs-disk_evicted both sit at advantage ~0.63 (CIs excluding 0.5 — a real residual, not closed), while ram_evicted-vs-disk_evicted closed to 0.53 (CI touching 0.5). Doubling the margin to T_MAX=300ms (also n=200) helps but does not close it either: advantage drops to ~0.56-0.57 on the hot-vs-evicted comparisons and to 0.50 (fully closed) on the which-tier comparison. Padding helped substantially (from a perfect channel) but did not close the hot-vs-evicted distinction at either margin tested. See §5.6 for the mechanism investigation.
- **Timing noise injection.** We have direct empirical evidence this is a *weak* mitigation on its own: §4.5 shows the primary existence channel survives realistic queueing-delay-scale noise and fully recovers to AUC=1.0000 with only 3 averaged probes. Noise injection would need to impose delay variance large enough that even repeated-probe averaging cannot recover the signal — a threshold this paper's data suggests is higher than naturally-occurring load noise, meaning deliberate noise injection would need to be substantial, with a corresponding latency cost, to be effective on its own.
- **Traffic-pattern anomaly detection.** The prime-and-probe protocol has a distinctive shape — rapid, repeated requests to a small set of adapters immediately followed by requests to a specific different adapter, repeated over many rounds — that is unlike typical single-adapter usage patterns and is, in principle, detectable at the platform level without any per-request latency cost. We view this as the most deployable low-cost mitigation given our results, though we have not built or evaluated a detector, and a sufficiently patient or low-rate attacker (§4.6's realistic-traffic result shows the underlying signal survives sparse, non-bursty probing) may evade a naively-tuned one.
- **Larger cache sizes.** §4.6 directly shows this does *not* eliminate the channel (AUC=1.0000 held at `max_loras`∈{1,2,4}) — it only raises the number of distinct filler adapters an attacker needs to control, a cost-raising measure, not a structural fix.
- **Batch-invariant kernels.** Directly and completely closes the *output-perturbation* confound (§4.4) — but this is a different problem from the timing channel itself; under this configuration, the experiment isolates the timing channel from the measured output-perturbation confound (no observed side effect on victim outputs); it does not make the leak *stop happening*. We flag this distinction because the two are easy to conflate: a platform enabling batch-invariant kernels has made the channel more precisely characterizable as a leak, not less exploitable.
- **Random or tenant-partitioned cache replacement (instead of LRU), and per-tenant slot reservation.** Discussed here, not evaluated experimentally — implementing either requires patching vLLM's actual scheduler/eviction internals, a materially larger engineering lift than a client-side proxy. Future work.

**Table 8. Mitigation tradeoffs on three axes — measured where we could, principled-estimate where we could not, and marked accordingly.**

| Mitigation | Channel | Residual advantage | Latency cost | Cache-capacity cost | Status |
|---|---|---|---|---|---|
| Constant-time padding | Residency (RQ1) | 0.56-0.63 on both hot-vs-evicted comparisons at T=150/300 (real, not closed at either margin); 0.50-0.53 on the finer which-tier comparison (closed) | High (>5x on the hot-case common path at T_MAX=150) | None | **Measured** (§5.6), both T=150 and T=300 |
| Namespace isolation, at two CPU-tier headroom settings | Occupancy (Scenario B) | 0.79 with generous headroom to 0.99 with a tight tier | None | Generous-headroom variant: moderate (extra host RAM, not GPU memory) | **Measured** (§5.5) — one measurement, reported at two settings, not two independent mitigations |

Namespace isolation's 0.79-0.99 (Scenario B occupancy channel) and constant-time padding's ~0.63 (RQ1 residency channel) are measurements of two *different* channels and are not directly comparable on the "residual advantage" column alone — a reader should not conclude one mitigation "beats" the other from this table.

The CPU-tier-headroom row is the same measurement as namespace isolation's residual channel, read the other direction: §5.5 shows Scenario B's advantage falls from 0.99 to 0.79 when `max_cpu_loras` is generously provisioned rather than tight. That is a defensive recommendation, not only an attacker-favorable tuning parameter — provisioning host RAM headroom for the CPU tier costs cheap, non-GPU memory and zero latency, against padding's 5-10x latency tax and reservation's direct sacrifice of the shared GPU cache capacity multi-LoRA serving exists to provide. It does not close the channel (0.79 is still a real, usable signal), so we present it as a cheap complement to, not a replacement for, the other rows.

Reservation remains the candidate that, on paper, could dominate every row on residual advantage and latency cost simultaneously, at the cost of the GPU cache capacity multi-LoRA serving exists to conserve — the most promising direction for a follow-up defense evaluation.

No single mitigation above is free, and the clearest actionable takeaway is layered, not a single fix: namespace isolation closes the strong identification claim (RQ3) but leaves a measured, real, weaker occupancy channel (§5.5, advantage 0.79) that itself resists naive constant-time padding on the disk-tier path specifically (§5.6, residual advantage 0.64) — closing this channel completely likely requires either a genuine architectural change (dedicated slots / reservation) or accepting a real, and per our measurements only partially effective, latency cost.

### 5.5 Scenario B, measured — the paper's central claim: does the attack survive the obvious fix?

§2 named Scenario B (per-tenant authorization gating adapter selection) as the deployment condition under which RQ3's identification claim does not apply, and stated that a weaker existence/activity channel *might* survive via indirect cache contention. We measure it here.

**Design.** The attacker owns exactly `max_loras` (2) adapters and touches only those, round-robin, never naming or probing the victim's adapter at any point. Under pure self-traffic and LRU eviction with #attacker-adapters == max_loras, neither of the attacker's own adapters should ever be evicted by the attacker's own activity — there is no third adapter competing for the two slots. If a real victim (an adapter the attacker never names) becomes active, the victim's request needs a cache slot too, evicting whichever of the attacker's own adapters was least-recently-used, purely as a side effect of shared-cache contention. The attacker detects this by probing *only its own* adapter and checking whether it comes back unexpectedly slow — a signal that can, at best, say "someone else was active," never *who*.

**Result at the default configuration: a real, weaker signal.** Self-probe latency: idle mean 35.47ms (std 5.06) vs. active mean 40.96ms (std 4.16) — a genuine ~5.5ms gap, not the ~50ms+ gap RQ1's disk-eviction tier shows. Threshold-free **AUC = 0.7875, 95% CI [0.645, 0.930]** (Hanley-McNeil, n=20/class — a wide interval, honestly reported rather than treated as a precise point estimate at this sample size). Accuracy at the Youden's-J-optimal threshold (36.05ms) is 72.5%; we flag this specific number as train-set-optimistic (the threshold was chosen from the same data it is scored on) rather than report it as if held out.

**This is a floor, not a ceiling.** The config above (only 3 distinct adapters ever touched, `max_cpu_loras=4` giving ample headroom) is close to the most defender-favorable case, since it lets the victim's eviction land softly in the RAM tier rather than push through to disk. Production deployments run far more adapters against a proportionally tighter CPU tier — the tier fills, evictions reach disk, and the gap should widen toward RQ1's ~50ms+ disk-tier separation. Re-running the identical protocol with `max_cpu_loras` tightened from 4 to 2 (removing all RAM-tier headroom, so the victim's request necessarily evicts the attacker's adapter all the way to disk) gives **AUC = 0.9875, 95% CI [0.952, 1.000]** — active mean 130.27ms vs. idle mean 38.20ms, a genuine disk-tier-scale gap. **Signal strength here is a tunable function of a cache-sizing parameter that operators do not currently think of as security-relevant.**

**Multi-round detection.** A real attacker does not stop at one probe, and does not threshold each probe individually before combining them — hard-decision majority voting throws away most of the information in each reading. The better estimator averages raw latencies across rounds before making one decision. Single-probe separation at the default configuration is d′=1.22 (mu_active=40.96, sd=4.06; mu_idle=35.47, sd=4.93); averaging k rounds scales separation by √k. Bootstrap-simulating mean-combining with a threshold recalibrated to the midpoint of the two class means (38.22ms, not the single-shot Youden threshold, which sits close to the idle mean and is tuned for single-shot balanced accuracy specifically) gives:

| Rounds (k) | 1 | 3 | 5 | 7 | 10 | 15 |
|---|---|---|---|---|---|---|
| Mean-combining accuracy | 69.8% | 85.5% | 92.0% | 94.8% | 97.5% | 99.2% |

This is a materially stronger result than an earlier majority-vote analysis suggested (which plateaued around 85% by round 15) — the gap between the two estimators is the threshold choice, not the underlying channel: Youden's threshold optimizes single-shot balanced accuracy, not multi-round combining, and sits close enough to the idle mean that idle-class single-shot accuracy is only ~55%, dragging down majority-vote's convergence rate. We report mean-combining as the correct estimator for this scenario and note the majority-vote number only to show how much a suboptimal combining rule can understate a channel using identical data.

This estimate assumes probing rounds are i.i.d., obtained via bootstrap resampling from n=40 single-shot trials rather than from genuinely sequential data; thermal drift, GPU queue state, and temporal correlation in real (non-simulated) victim traffic could all violate that assumption, so we report it as an upper-bound estimate pending real sequential verification, not a claimed field result. A genuinely uncontaminated sequential design is available and left for follow-up: alternate probes between the attacker's two owned adapters (A, B, A, B, ...) rather than re-probing the same one — each probe reloads its own target while the other remains the LRU eviction candidate, so consecutive readings are not self-warmed the way repeatedly probing one fixed adapter would be.

**What this does and does not establish.** Blocking cross-tenant adapter naming (closing Scenario A) does not eliminate the channel — a real existence/activity signal survives via pure cache contention, requiring no naming capability at all, and its strength ranges from a modest AUC=0.79 (RAM-tier-favorable config) up to AUC=0.99 (disk-tier-forcing config), depending on a cache-sizing parameter the attacker does not control but a defender does. It does not, and cannot, tell the attacker *which* tenant was active among possibly many; Scenario B is fundamentally an occupancy/volume channel, not an identification channel.

**One assumption this design makes, stated rather than left implicit.** The attacker's protocol assumes knowledge of `max_loras` (to own exactly that many adapters). This is cheaply learnable rather than privileged knowledge: an attacker can discover it by self-experimentation — incrementally registering and touching its own adapters until self-eviction begins, at which point the count just before onset reveals `max_loras` directly. We do not measure this discovery process, but note it closes what would otherwise be an unstated assumption.

**Does this survive realistic contention? We tested it, since this was the single most important remaining validity question against the paper's central claim — and getting the answer right took two attempts.** Every Scenario B measurement above is idle-GPU. We re-ran the tight-headroom protocol at production cache scale on native storage (`max_loras=8, max_cpu_loras=8`, zero CPU-tier headroom — the config our own §5.4 recommends *against* as a defense, so this tests the attacker-favorable case; whether generous headroom changes the picture under contention is untested) under the same 6-worker concurrent contention §4.5 uses (noise workers hit a separate 8-adapter pool, excluding the attacker's 8 adapters and the victim — though this still conflates queueing delay with cache-tier pressure, the same property §4.5's contention has). Idle-GPU baseline at this exact configuration: **AUC=1.0000 [1.000, 1.000] (n=40)** — even cleaner than the small-scale tight result above, consistent with zero headroom forcing disk-depth eviction every time.

**First attempt (n=40) reported a result we should not have trusted, and we corrected it before it went further.** A first run gave single-probe threshold-free advantage 0.57 [0.38, 0.76], and a bootstrap projection (resampling only the aggregated groups, not the original 40 trials) suggested aggregation climbed to advantage 0.95 by 30 rounds. Both numbers turned out to be artifacts of a small sample: the single-probe CI already included values consistent with no effect, and projecting an aggregation curve from a point estimate whose own interval spans "no effect" inherits that uncertainty rather than resolving it — the curve's own confidence interval at every N, computed correctly by resampling the original 40 trials rather than just the derived groups, in fact touched or nearly touched 0.5 throughout. We re-ran at n=200 rather than report the projection.

**n=200: the effect does not survive scrutiny, and we report that directly rather than the more convenient first result.** Single-probe threshold-free AUC is **0.4502 [0.3695, 0.5311]** — advantage 0.5498 [0.4689, 0.6305], an interval that includes values *below* 0.5. Active and idle means have nearly converged under this contention level (64.20ms vs. 65.50ms) — compare the idle-GPU gap of 36.71ms vs. 21.42ms. This is a different failure mode from RQ1's contention degradation (§4.5), where the underlying gap survives at a noisier scale and aggregation recovers it: here the gap itself appears to collapse, not merely get buried in noise. Directly measuring aggregation by grouping consecutive same-label trials (not bootstrap-projecting) gives advantage 0.595 [0.505, 0.738] at N=5 (20 groups/class), 0.550 [0.500, 0.730] at N=10 (10 groups/class), and 0.600 [0.520, 0.840] at N=20 (5 groups/class) — flat and noisy, not a climbing trend, every interval touching or nearly touching 0.5. **We do not have evidence that aggregation reliably recovers this signal under this specific contention level, and we are not claiming that it does.**

**A plausible mechanism, stated as a hypothesis rather than a confirmed finding.** Scenario B's detector depends on the attacker's own adapters holding a stable, self-tracked LRU ordering across the GPU tier. Background contention from *any* other tenant's traffic — not only the specific victim's — competes for the same bounded tier and can disrupt that ordering regardless of whether the victim is active, which would make this channel more contention-fragile than RQ1's simpler hot-vs-fully-evicted distinction. We have not isolated this mechanism from plain queueing-delay noise, and flag it as the most likely explanation, not a demonstrated one.

**The honest scope, corrected from our first attempt.** The central claim is measured, real, and strong on an idle GPU (AUC=0.79-1.00 depending on cache headroom). Whether it survives *this specific* contention level is, at the sample size collected, an open question rather than a demonstrated success: single-probe detection is not reliably better than chance, and we do not have solid evidence that aggregation rescues it. This is a genuine limitation of the central claim, not a caveat resolvable with better statistics on the data already in hand — more trials, an isolated (non-shared-capacity) noise pool, and a lower contention level are the concrete next steps (§8).

**Demonstrating the volume claim under Scenario B specifically remains open work.** We measure existence/activity (a binary signal) at two cache-headroom configurations here, not a volume estimate across a range of victim request rates under the self-eviction-only design. §4.6 demonstrates detection frequency tracking victim request rate directly (strong presence/absence detection plus a real, more modest gradient among nonzero rates specifically) — the concrete "infer a competitor's traffic volume" scenario from §1 — but using Scenario A's direct-naming protocol; a Scenario-B-specific version of that sweep is the natural next experiment and is not included here.

### 5.6 Defense evaluation, measured: constant-time response padding — and a genuine analysis error we caught and corrected

§5.4 discussed mitigations without evaluating any experimentally. We evaluate the most classical candidate — constant-time (padded) response latency — via a client-side proxy: measure true completion latency, and if under a ceiling `T_MAX`, block until an **absolute deadline** (`t0 + T_MAX`, recorded at request arrival), busy-waiting the final ~1ms. This implementation choice matters: an early version instead slept a *computed remainder* (`T_MAX − true_latency`), which re-leaks the residency bit — `sleep()` overshoot scales with sleep duration, so a hot request's longer remainder accumulates more overshoot than an evicted request's shorter one, inverting rather than erasing the signal. A non-pooled HTTP client was also found and fixed along the way (accumulating connection overhead over long sessions), though it turned out not to be the deeper cause of the T_MAX=300 instability discussed below. We report both fixes because they are specific, checkable pitfalls anyone building a similar proxy will hit. The relevant scoring metric throughout is **distinguishing advantage**, `max(AUC, 1−AUC)`, not raw AUC — noise alone gives AUC≈0.5, not a value pinned near 0 or 1, and an early analysis pass that used raw AUC nearly mistook a real 0.85-0.89 residual for near-total closure.

Cost: at T=150, every hot request (~27ms true) now takes >5x longer — padding buys latency, not throughput, a different axis from cache reservation's capacity cost (§5.4). Quantized (bucket) padding remains implemented but not experimentally validated (§5.4).

## 6. Related Work

### 6.1 LLM-serving timing side channels

The closest prior work targets a *different* layer of the same broader system: shared key-value (KV) and prefix caches, used to accelerate repeated or overlapping prompt processing across requests. PromptPeek, EarlyBird, and InputSnatch each exploit variants of this mechanism to reconstruct a victim's *prompt content* — by probing time-to-first-token or scheduling-priority effects that arise when an attacker's guessed tokens share a cache-hit prefix with a victim's actual prompt. A single-author defense proposal, "Governing the KV Cache: Preventing Timing Side-Channel Leakage in Multi-Tenant LLM Inference" (posted about a month before this draft, not a comprehensive field survey), synthesizes these three attacks and proposes mitigations at the level of cache-key computation. We read it closely rather than cite it only as a scoping check, and it complicates a clean "prior work leaks content, we leak identity" story: its own adversary-goal taxonomy (§3.4/Table 2 of that paper) distinguishes *confirmation* (is a specific value cached right now? — one request, O(1)) from full *reconstruction*, and states plainly that confirmation "repeated against a list of known identifiers... enumerates which subjects were served, and when, without recovering a single token of anyone's prompt." That is an identity-and-activity leak, at the KV-cache layer, already contemplated in the closest adjacent work — not something only our channel produces. SafeKV targets the same class of cross-tenant KV-cache leakage specifically, and independent fuzzing-based vulnerability discovery work has found concrete cross-request state-corruption bugs (not timing side channels, but related isolation failures) in production serving systems' KV-cache handling.

Given that, the distinction this paper actually rests on is *layer*, not *leaked-fact category*: every attack and defense proposal above operates on cache keys computed over token sequences, and even KVGov's proposed cache-key-computation mitigation would not touch a channel whose root cause is residency in the adapter-management cache — a structurally different resource, keyed on tenant/adapter identity rather than prompt content. We do not claim to be the only channel capable of identity/activity leakage in multi-tenant LLM serving — KVGov's own taxonomy shows the KV-cache layer can produce one too — only that this specific layer, adapter management, has not been studied as a timing side channel prior to this work.

### 6.2 Multi-LoRA serving systems

We checked each commonly-cited system's actual documented architecture rather than assume they share vLLM's mechanism: only **LoRAX** documents something close to vLLM's GPU/CPU/disk LRU hierarchy (a vendor blog names a "Tiered Weight Caching" feature; we could not confirm the scheduler at the source level), **S-LoRA** is two-tier with predictive prefetch and no LRU terminology anywhere in its own paper — correcting a secondary-source claim ("global LRU eviction") we searched for and could not substantiate — and **Punica** documents no eviction policy at all, contributing batched CUDA kernels rather than a cache hierarchy. This paper's claims are about vLLM's specific mechanism; the general bounded-fast-tier-with-fallback pattern is common across the field, the exact three-tier LRU hierarchy is not.

### 6.3 LoRA-specific memorization and extraction attacks — a different attack class, explicitly distinguished

A separate line of work studies whether LoRA fine-tuning itself leaks training data, via classic extraction/memorization attacks (prompting a model to regurgitate memorized sequences) rather than timing. "Leaner Training, Lower Leakage: Revisiting Memorization in LLM Fine-Tuning with LoRA" studies exactly this question and finds LoRA fine-tuning *reduces* memorization relative to full fine-tuning; StolenLoRA and related work study extracting an adapter's learned behavior via synthetic-data probing. We surfaced this literature early in scoping this project specifically to rule out a naive "does LoRA leak its training data" framing as already answered — it is, by that line of work, and it is not what this paper studies. Our channel does not require, and does not provide, any access to a victim adapter's trained content or behavior; it leaks residency, identity, and configuration (rank) via timing alone, a disjoint threat from content memorization.

### 6.4 Side-channel methodology lineage

The prime-and-probe measurement pattern (§3.3, RQ2/RQ3) is not novel as a *technique* — it is the standard structure of cache-based side-channel attacks in the architectural security literature (evict a shared resource, wait, re-probe to detect whether it was refilled), long used against CPU cache hierarchies and, more recently, GPU-resident state. Nor, we note directly rather than let a reviewer find it first, is the *escalation* from "the resource was touched" to "which of several principals touched it" unprecedented at the conceptual level: two recent, closely related results make the same move against a different resource. GateBleed exploits power-gating timing on Intel AMX accelerators to infer which expert a mixture-of-experts (MoE) model routed a given input to, reporting 100% accuracy on expert-choice leakage; MoEcho (CCS 2025) attacks MoE serving via CPU cache-occupancy and GPU performance-counter/TLB side channels to reconstruct routing-dependent information about a victim's prompts. Both target routing-table residency in an MoE model — which expert is active — rather than adapter residency in a multi-tenant LoRA cache, but the underlying inferential structure (which of several internal components handled this request, read from a shared resource's timing trace) is the same idea we apply here.

The distinction that survives is deployment model, not concept. Both GateBleed and MoEcho require an attacker process co-located on the same physical host as the victim, with access to hardware-level timing primitives — AMX power-gating events, cache-occupancy counters, performance counters, TLB state — that only a co-resident process, not an ordinary remote API client, can observe. Our attacker needs none of this: no co-location, no hardware counter access, no privileged instrumentation, only wall-clock timing of its own ordinary HTTP responses. We therefore do not claim the inferential move (activity → identity, among several principals sharing a resource) is new; we claim it is achievable at the adapter-management layer, over an unmodified remote API, by an attacker with nothing beyond a paying customer's credentials — a materially weaker and more portable attacker model than either MoE-routing result requires.

| **This work** | **Adapter management cache** | **Residency (reload) timing, unmodified remote API** | **No** | **Victim's identity, activity, and adapter configuration** |

Read this way, our distinguishing claim is narrower, and more defensible, than "we leak identity, they leak content": we are the only row producing identity/activity/configuration-level leakage at the adapter-management layer specifically, and the only identity-capable row (alongside KVGov) that requires zero co-location — the same property that separates us from the MoE-routing results, which achieve identity-level inference but pay for it with a privileged, co-resident attacker position we do not require.

## 8. Limitations and Conclusion

**Hardware and serving-engine scope.** Every experiment runs on one consumer GPU (RTX 4060 Laptop, NVIDIA) via one serving engine (vLLM). Three base models replicate the two central claims (§4.6), addressing model-specificity, not hardware-vendor-specificity; cross-GPU-vendor and datacenter-hardware validation remains future work. §6.2's verification of S-LoRA/Punica/LoRAX's actual documented architectures found real differences in eviction mechanism across systems — the general pattern (bounded fast tier, slower fallback) is common, vLLM's specific GPU/CPU/disk LRU hierarchy is not universal, and our claims are about the latter, not the former.

**Production-scale cache configuration was the critique we expected to be hardest to answer, and it held up.** Every result in §4.1-§4.5 uses `--max-cpu-loras 4`, chosen to make the disk-eviction tier reachable with a small number of filler adapters, while vLLM's own default for this setting is `max_num_seqs` — commonly tens to hundreds in production. §4.6 measures this directly at `--max-loras 8 --max-cpu-loras 64` (67 registered adapters): RQ1's existence signal remained near-perfectly separable (AUC 0.97-1.00 across all three comparisons) and RQ3's identification held at 90.0% (down from 98.3%, with the drop traced to threshold calibration, not signal loss). This was an idle-GPU, n=30/40, single-session result; contention-robustness at RQ1/RQ3's production-scale config specifically remains untested, though §5.5 now measures contention-robustness for the paper's central claim (Scenario B) at a production-scale tight config, below.

**Scenario B under contention was the single most important remaining validity question, and the honest answer is that it is unresolved, not solved.** §5.5 reports this at production scale (`max_loras=8, max_cpu_loras=8`, the attacker-favorable zero-headroom config) on native storage: idle-GPU signal is AUC=1.0000 (n=40), but under 6-worker contention (n=200, after a first n=40 attempt wrongly suggested recovery via aggregation and was corrected) single-probe advantage is 0.55 [0.47, 0.63] — CI includes below-0.5 — and directly-measured aggregation up to N=20 shows no reliable climb (0.55-0.60, every CI touching 0.5). Active and idle means have nearly converged under this contention level, unlike RQ1's degraded-but-preserved gap, suggesting a genuinely different, more severe failure mode, plausibly because Scenario B's detector depends on a self-tracked LRU ordering that any competing traffic can disrupt (a hypothesis, not confirmed). Concrete next steps: substantially more trials, an isolated noise pool that doesn't share GPU-tier capacity with the attacker's own adapters, and a lower contention level. This is a genuine, currently-open limitation of the paper's central claim, not a resolved result.

**Severe contention overwhelms fixed-threshold detection, and may suppress the measurable Scenario-B signal — these are different failure modes, not one.** §4.5 diagnoses RQ2/RQ3's contention failure precisely: RQ2's activity signal is genuinely overwhelmed by queueing noise and does not recover with aggregation, while RQ3's is a static threshold miscalibrated against an inflated absolute scale (partial fix: concurrent-paired-canary; a fully adaptive rolling-window threshold is identified but not implemented). Scenario B's contention failure (§5.5) is presently unresolved rather than diagnosed to this precision — we do not yet know whether it is a threshold problem, a genuinely suppressed signal, or both. §4.5's specific "build around the disk tier, not the RAM tier" recommendation was calibrated on that section's small-scale, 9p-bridged configuration; whether it holds at production cache scale or on native storage, where the RAM tier shows comparable or stronger idle-GPU separation (§3.7, §4.6), is untested under contention.

**T_MAX=300ms is now measured and reliable; quantized padding is not.** §5.6's original T_MAX=300ms measurements showed instability we traced to host GPU power throttling on battery power (roughly 30-35% of the rated 115W budget, confirmed via `nvidia-smi -q -d POWER`), not the proxy or WSL2. With the machine confirmed on AC power at both ends of the run (140W, logged) and lingering server processes killed before relaunch, the re-run (n=200) was clean: `hot`/`ram_evicted` reads a tight 301.9ms (std ~1ms) with no spikes, and the distinguishing-advantage residual (0.568/0.563/0.502, Table 9) is now a real, reportable number rather than an open question. Quantized (bucket-based) padding was not re-attempted under the corrected power state and remains implemented but not experimentally validated, as originally reported (§5.4, §5.6).

**The motivating volume scenario is demonstrated under Scenario A as presence/absence detection, with only a modest rate gradient, not yet under Scenario B.** §4.6's six-point sweep shows strong idle-vs-active detection (6.7% false-positive rate, 73-100% detection once any traffic exists) and confirms this is not solely an artifact of the idle-vs-nonzero step: a direct recompute restricted to the five nonzero rates alone still shows a significant, if weaker, gradient (ρ=0.25, p=0.031 on detection; ρ=-0.43, p=0.00012 on raw latency) — we checked this specifically rather than let the full-sample ρ=0.55 overstate a graded response. A first attempt at this sweep used a blocked (non-randomized) rate order and was discarded after we checked, and confirmed, that it confounded rate with session-order; the corrected, randomized-order, canary-verified re-run is what §4.6 reports. A Scenario-B-specific (self-eviction-only) version of this sweep remains untested.

**Identification at larger tracked-set sizes was tested once, at n=80, and held — but at an easier task, not a harder one.** §4.6 extends RQ3 from two named adapters (four classes) to eight (single-label 8-way, exactly one of eight active): 100% accuracy (80/80, Wilson 95% CI [95.4%, 100%]), with probe cost scaling linearly (8 probes/trial) but no accuracy degradation observed. This should not be read as identification getting easier at scale: single-label argmin has no threshold to calibrate, which is exactly where the four-way design's errors came from. The realistic multi-label task — any subset of eight tenants active, 2⁸ possible states, requiring per-adapter absolute thresholds like the four-way design — is untested, as is whether accuracy holds at substantially larger tracked-set sizes (dozens to hundreds of adapters, closer to a real platform's tenant count).

**No real commercial-platform validation.** Every result is on infrastructure we control; a self-owned-adapters-only test against a commercial multi-tenant LoRA host (Predibase/LoRAX, Fireworks, Together, or similar) remains the clearest remaining external-validity gap and the natural next step, to be pursued only with that platform's authorization (§7).

**No pre-registered power analysis.** Sample sizes were increased iteratively (e.g., 30→40→60→120 for RQ3) as results warranted more confidence, not chosen from an a priori power calculation — standard practice for exploratory systems-security work, but worth stating plainly rather than implying otherwise.

**Conclusion.** Multi-LoRA serving's shared, bounded adapter cache is a deliberate architectural response to a real scaling constraint — and, we show, an information channel an unprivileged co-tenant can read from ordinary request timing alone, with no access to any other tenant's prompts, outputs, or cache keys. The channel's foundational form (§4.1-§4.2, §5.5) requires nothing beyond an ordinary API credential and survives the removal of cross-tenant adapter naming on an idle GPU; under severe shared contention, however, this signal becomes substantially less reliable and remains an open robustness question (§5.5). Its strongest form (§4.3) requires that specific, avoidable misconfiguration to be present. Both are real, both are measured, and neither is free to fix: every mitigation we evaluate (§5.4-§5.6) trades away either cache efficiency, latency, or — in the case we measured most carefully — only partially closes the gap it targets. We hope the layer-level framing (§6) generalizes: any serving system that multiplexes tenant-distinguishing state through a shared, bounded, reactively-evicted cache should expect the same class of channel, whether the cached unit is a LoRA adapter, a routed expert, or something not yet built.
